# `pm_mcp_server` — Generic Metadata-Driven Python MCP Server

A generic, metadata-driven Model Context Protocol (MCP) server written in Python to seamlessly integrate an AI Agent with an existing ASP.NET Core/.NET application.

`pm_mcp_server` replaces hardcoded, endpoint-specific tool sprawl with four generic MCP tools operating against a dynamic runtime registry combining OpenAPI technical specifications with YAML business metadata.

---

## 1. Core Architecture and Responsibilities

Instead of generating separate MCP tools for 70+ to 300+ APIs, `pm_mcp_server` exposes four generic tools:

| MCP Tool | Primary Responsibility | Agent Usage Policy |
|---|---|---|
| `search_apis` | Natural language business metadata search over descriptions, keywords, synonyms, and use cases. | **First Choice / Preferred**: Agents must ALWAYS try search first. |
| `get_api_schema` | Combines technical OpenAPI contract with YAML business documentation and dependency mappings. | Used after finding an API candidate to inspect required inputs. |
| `execute_api` | Enforces read-only policy, validates arguments server-side, checks JWT expiration, and executes the call. | Used to invoke an approved operation with validated arguments. |
| `list_all_apis` | Full-catalog paginated browser including unapproved and disabled endpoints. | **Fallback Only**: Used ONLY when search fails or is insufficient. |

```
AI Agent -> [search_apis] -> [get_api_schema] -> [execute_api] -> .NET API
                 |
                 +-> (if search insufficient) -> [list_all_apis]
```

## 2. API Identity: Composite Key `(endpoint_name, method)`

In accordance with system design requirements:
- **No synthetic IDs, numeric IDs, or UUIDs are generated or used.**
- Every API is uniquely identified across the entire system by the tuple:
  ```python
  (endpoint_name, method)
  ```
- `endpoint_name`: Either the OpenAPI `operationId` or a deterministic PascalCase name derived from HTTP method and path segments (e.g. `GetApiSuperusers`).
- `method`: Normalized uppercase HTTP verb (e.g. `GET`, `POST`).

---

## 3. Contract Ownership: OpenAPI vs. YAML

- **OpenAPI** is the sole source of truth for the **technical contract**:
  - Paths, methods, parameter types, formats, defaults, enums, required fields, request body definitions, and response schemas.
- **YAML (`catalog/api_catalog.yaml`)** owns the **business & exposure metadata**:
  - Business descriptions, `use_when`, `avoid_when`, keywords, synonyms, abbreviations.
  - Domain categorization.
  - Approval state (`approved`, `pending_review`), enablement (`enabled: true/false`), and access mode (`read_only`).
  - Inter-API dependencies (`dependent_apis`).

---

## 4. Modeling API Dependencies (`dependent_apis`)

When an operation requires an input that is generated by an upstream API:
```yaml
dependent_apis:
  - endpoint_name: "SearchProjects"
    method: "GET"
    purpose: "Retrieve the projectId required by this endpoint."
    output_to_input:
      "response.projectId": "path_params.projectId"
```

### Dependency Behavior:
1. `search_apis` surfaces dependency hints.
2. `get_api_schema` returns detailed input/output mapping guidance.
3. The server **never executes chains of APIs automatically**. The AI agent discovers the dependency, calls the upstream endpoint via `execute_api`, extracts the identifier, and then invokes the downstream endpoint.
4. Circular dependencies are detected and rejected at startup.

## 5. Security & Authentication

### Inbound MCP JWT Expiration Check
- The server checks **only whether the inbound JWT has expired** via the `exp` claim.
- **Important Security Limitation**: Checking the `exp` claim without cryptographic signature verification **does not verify token authenticity or issuer trust**. It is solely a freshness sanity check.
- The downstream ASP.NET Core API remains the sole authority for downstream authentication and authorization.

### Downstream Credential Isolation
- Inbound MCP tokens are **never forwarded** blindly to the downstream .NET API.
- If downstream credentials are required, they are managed via explicitly configured server-to-server mechanisms.

### Read-Only Enforcement
- Only operations with HTTP method in `{"GET", "HEAD", "OPTIONS"}`, `access_mode: "read_only"`, `enabled: true`, and `approval_status: "approved"` may execute.
- All mutating verbs (`POST`, `PUT`, `DELETE`, `PATCH`) are unconditionally rejected.

## 6. Future RAG Extensibility

The search architecture decouples tool registration from the retrieval backend:
- `ApiSearchService` (service facade)
- `SearchBackend` (protocol / interface)
- `YamlKeywordSearchBackend` (active keyword search implementation)
- Future `RAGSearchBackend` (prepared configuration schema; currently disabled via validation guard).

When RAG is disabled (`rag.enabled: false`), the application runs without any LLM or embedding provider credentials.

## 7. Quickstart

### 1. Installation
```bash
pip install -r requirements.txt
```

### 2. Catalog Synchronization from OpenAPI
Discover live endpoints from the configured Swagger UI (`http://localhost:5273/swagger/index.html`):
```bash
python catalog/sync_from_openapi.py
```

### 3. Run the MCP Server
Start the server using Streamable HTTP transport:
```bash
python -m server.app
```
Endpoint available at: `http://127.0.0.1:8000/mcp`

For STDIO transport:
```bash
PM_MCP_TRANSPORT=stdio python -m server.app
```
